## What agent_ro can and cannot do (layer 1)

Tested in `tests/test_sources.py`, every statement sent straight to the database, without validation.

| | SQL Server | PostgreSQL |
|---|---|---|
| Account | member of `db_datareader` only; no writer, owner or sysadmin role | no superuser, create-role or create-db right; `SELECT` grants only |
| `INSERT` / `UPDATE` / `DELETE` / `TRUNCATE` | refused (no permission) | refused (read-only transaction by default, **and** no grant) |
| `CREATE TABLE`, `SELECT INTO` a real table, `DROP` | refused | refused |
| `xp_cmdshell`, `COPY … TO` a file | refused | refused |
| Turn the read-only default off (`SET default_transaction_read_only = off`) | n/a | **allowed**: one `SET`. Writes on real tables are still refused by the grants |
| Temporary tables | **allowed**: `SELECT … INTO #tmp` (tempdb is open to every login) | **allowed** once the default is off |
| Query timeout | none server-side | `statement_timeout` = 30 s |
| Personal data | n/a | `national_number`, `iban`, `street_address` of `employees` unreadable; so `SELECT *` on `employees` fails |

Consequences for step 11: the grants are the layer that really protects the data. Validation must still refuse
`SELECT INTO` (temp tables), `EXEC`, `SET` and multiple statements; SQL Server needs a client-side timeout;
`get_table_card` must list only readable columns (`has_column_privilege`, as the catalog query does).

## Traps found while answering the 12 starter questions

| Q | Trap | Right reading |
|---|---|---|
| 1, 11, 12 | Credit notes (`FAC_TYPE = 'A'`) are in `VTE_FACT` with **positive** amounts | Net revenue = invoices − credit notes |
| 2 | A credit note with reason `REGUL_TARIF` lists quantities (270 units for Distrinergie) but returns no goods | Units sold = invoiced − credit notes with reason `RETOUR` only |
| 3 | The reception line shows 0 refused; the return to the supplier is only a stock movement | `STK_MVT` type `RET` (negative), reference = the non-conformity |
| 4 | Two supplier records match "Kompra": `KOMPRA GMBH (NE PAS UTILISER)` | `find_values` must show both; the order identifies the right one |
| 5 | Classes 6 and 7 of 2025 sum to **0**: the appropriation entry (693000, 31/12) moves the profit to equity | Net result = classes 6–7 without 693000 |
| 6 | "EBITDA" has no column: it's a definition | Accounts 60–62, 64, 70–74; not 63 (depreciation, provisions incl. reversals), 65 (interest, bank fees), 66–67, 69. Margin = EBITDA / accounts 70 |
| 7 | Two sources of truth inside one database | Ledger account 630000 = depreciation register (`amortissement`): same total in 2025 |
| 8 | A contract row is one period (amendments are rows) | Count **distinct** people whose row covers the date; site via the department |
| 9 | One timesheet row per working day | `COUNT(*)` of `ACC` rows = working days |
| 11 | ERP and ledger differ for May 2026 | 23 invoices are `EMISE` (issued, not yet transferred to accounting): 352 505,79 €, exactly the gap |
| 12 | Staff number `10405` in the ERP, `M10405` in payroll; `rate` is a **percentage** (0.1000 = 0.1 %); a February correction run was paid in March | Normalize keys; the commission is on the `MENSUEL` run of the period |

Other things worth knowing:

- Code values are explained in `PAR_CODE` (ERP) and in column comments (accounting): statuses, movement types,
  credit-note reasons, regions. A table card should show them.
- Accounting: 12 draft entries (`BROUILLARD`) in May 2026; budget has versions (V1, V2, FINAL: only FINAL is approved).
- ERP data stops on 29 May 2026 (extraction on the 31st); payroll starts in June 2025.
- Three salespeople have no staff number (two people and the `SIEGE` pseudo-salesperson): no payroll link.
